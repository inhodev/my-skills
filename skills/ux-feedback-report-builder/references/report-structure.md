# 보고서 구조 명세

분량은 참가자 수로 정한다. **5명 = 20p, 8명 = 30p.** 다른 인원이면 아래 비율로 조정하되 사용자에게 먼저 확인한다.

## 페이지 순서 (30p 기준, 괄호는 20p)

| 순서 | 페이지 | 필수 구성 |
|---|---|---|
| 1 | 표지 | 시네마틱 다크. 로고 + "사용자 피드백 보고서"만. (`design-tokens.md` §표지) |
| 2 | 어떻게 테스트했나요? | 조사 목적 / 조사 방법 / 조사 개요 / 어떻게 분석했나요 / 이 리포트를 읽는 방법 + 서비스 **메인 화면 캡처 1장** |
| 3 | 먼저 핵심만 보면 | 요약 문단(tint) → "N명 중 M명" 통계 행 4~5개 → 주요 강점 / 주요 문제 → 참가자별 최종 판단 한 줄씩 → 맺음 인용 |
| 4~17 (4~9) | 주제 페이지 | 서비스 흐름 순서. 첫인상 → 핵심 기능 성공 → 핵심 기능 실패 → 오류 안내 → 후속 흐름 → 관리/일정 → 기기별 화면 → 부가 기능 → 신뢰 → 기존 방식 대비 → 특히 좋았던 점 → 이탈 지점. 앱에 맞게 가감 |
| 18~25 (10~14) | 참가자별 페이지 | 1인 1페이지 |
| 26 (15) | 여러 참가자에게 반복해서 나온 반응은? | 2명 이상 공통 반응 6~8개 카드 + 가장 많이 겹친 문제/긍정 인원표 + 맺음 인용 |
| 27 (16~17) | 지금 가장 먼저 고쳐야 할 5가지 | 1번은 전폭 카드, 2~5는 2열. 각 항목 "N명이 겪음" 표기 + 우선 보류 목록 + **수정 완료를 확인하는 방법**(재검증 시나리오 5줄) + 테스트에 실제 쓰인 데이터(있으면) |
| 28~29 (18~19) | 그다음으로 고칠 것들 | 주제별 박스 3~4개, 마지막에 "순서를 이렇게 권하는 이유" tint 박스 |
| 30 (20) | 그래서 무엇을 먼저 개선해야 할까? | 최종 결론 2문단 → 단기/중기/장기 3열 → 다음 테스트에서 확인하면 좋을 것 / 이 리포트의 한계 → 긴 맺음 인용(4~5문장) |

## 페이지 제목

- **질문형**: "처음 만났을 때 어떤 느낌이었을까?", "지원 흐름 차트는 이해됐을까?", "어디에서 멈추거나 나가고 싶어졌을까?"
- 강조어는 `<span class="em">`으로 브랜드색: "공고 링크 분석, <em>성공했을 때는</em> 어땠을까?"
- 예외적으로 평서형이 더 강한 페이지 하나 정도는 허용: "링크 하나에 서비스 전체가 막힌 순간"
- 앞 3장과 뒤 3장은 고정 제목: 어떻게 테스트했나요? / 먼저 핵심만 보면 / 여러 참가자에게 반복해서 나온 반응은? / 지금 가장 먼저 고쳐야 할 5가지 / 그다음으로 고칠 것들 / 그래서 무엇을 먼저 개선해야 할까?

## 2p "어떻게 테스트했나요?" 상세

- **조사 목적**: 서비스 핵심 경험이 처음 쓰는 사람에게 얼마나 자연스러운지 확인. **약점 기능을 목적에 미리 언급하지 않는다** (결과를 앞서 말하는 것처럼 보임).
- **조사 방법**: 참가자가 실제로 한 일을 순서대로, 하는 일 서술("~합니다"). "화면을 녹화했다"는 문장 넣지 않는다.
- **조사 개요**: 참가자 구성 / 플랫폼 집계 / 조사 일정. 총 녹화 분량·평균 시간 금지.
  - 인원: "테스트 참가 10명, 기록 상세 분석 8명(참가자 A ~ H)"처럼 표지 숫자와 본문 참가자 수를 잇는다.
  - 플랫폼: "iOS 3명 · iOS TestFlight 1명 · Android 1명" / "데스크톱 웹 3명 · 모바일 웹 5명"
- **어떻게 분석했나요**: 행위 서술 한 문단. "여덟 명의 녹화 영상을 처음부터 끝까지 돌려 보며 정리했습니다. 화면을 5초마다 잘라 1,100장 넘게 붙들어 놓고 발언과 맞춰봤습니다. 잘못 알아들은 이름은 화면과 대조해 바로잡았고, 뜻이 확실하지 않은 말은 싣지 않았습니다. 화면에 보인 계정 정보는 기록에서 뺐습니다."
- **이 리포트를 읽는 방법**: 4줄. 평가 대신 누가·어디서·뭐라고 / 점수 없음, 같은 자리에서 막힌 인원 / 빨간 네모는 저희가 그린 표시 / N명이 모든 사용자를 대신하지 않는다
- 캡처: 서비스 **메인 화면(대시보드)** 1장, 54mm, 오른쪽에 분석 방법·읽는 방법 박스.

## 3p "먼저 핵심만 보면" 상세

- 요약 문단: 검증된 가치 한 문장 → 문제의 핵심 두세 문장. 이 문단 하나로 보고서 전체가 요약돼야 한다.
- 통계 행(`.st`): 왼쪽 서술, 오른쪽 "8명 중 5명". 긍정 1개 이상 포함.
- 참가자별 최종 판단: 참가자당 한 줄, 그 사람의 결론적 태도(계속 쓸지, 어디서 막혔는지).
- 특정 기능을 끝까지 판 참가자가 있으면 강점 목록에 "참가자 H는 ~을 처음부터 끝까지 집중 테스트하고 ~라고 평가함"으로 특별히 짚는다.

## 주제 페이지 표준 구성

```
h1 (질문형)
p.intro (3~4문장 서술: 무슨 일이 있었나)
g2: box "잘 전달된 부분 / 잘 된 것" + box "걸린 부분 / 막힌 것"   (ul.li 3~4개씩)
shots (--ih:84mm): cap(캡처+마크) + side(qs 인용 3~4개)
shots (--ih:58mm): cap(캡처) + side(box.tint 관찰 정리)       ← 필요시
```

- 인용은 페이지 주제와 직접 관련된 것만. 같은 인용을 다른 페이지에서 반복하지 않는다(참가자 페이지 제외).
- 캡처는 페이지당 1~3장. 캡처가 없는 주제 페이지는 인용·관찰 카드로 채우되, 캡처 없는 페이지가 연속 2장 이상이면 배치를 다시 본다.
- 캡처 행 오른쪽 `.side`는 `flex:1`. 이미지 옆이 비면 관찰 정리 박스를 넣는다.

## 참가자 페이지 표준 구성

```
h1 "참가자 A는 어떻게 느꼈을까?"
box.tint 한 줄: "참가자 A · 데스크톱 웹"       (플랫폼만. 연령·성별·기기 모델 금지)
box 첫인상 (2~3문장)
box 탐색 흐름 (화살표 →로 이은 한 줄)
g2: 긍정 포인트 / 망설임·불편 지점  (ul.li)
qs 인용 3~4개 (이 페이지에서는 참가자 표기 생략 가능)
box.tint 총평 (2문장)
```

- 참가자 페이지에도 캡처를 1장 넣을 수 있다(그 참가자만의 장면). 넣으면 인용 옆에 배치.
- 8명 페이지의 첫인상·총평은 서로 다른 문장으로. 복붙 티가 나면 안 된다.

## 뒤 3장 상세

**여러 참가자에게 반복해서 나온 반응은?**
- 카드 제목은 번호 + 짧은 명제: "1. 링크 분석은 관문이다", "3. AI 기능은 가치보다 발견성이 낮다"
- 본문에 참가자 알파벳을 괄호로 표기: "실패한 세 명(B·D·G)은…"
- 하단 인원표는 문제/긍정 4개씩.

**지금 가장 먼저 고쳐야 할 5가지**
- 각 항목: 제목 + 인원 태그(brand color, 8.4px) + 무엇을 어떻게 고칠지 2~3문장.
- "우선 보류해도 되는 것" 3개: 고객이 하고 싶어할 만한 것 중 지금은 아닌 것.
- "수정 완료를 확인하는 방법": "새 참가자 한 명에게 아래 흐름을 시켜 보고, 막힘 없이 끝까지 통과하면 이 단계는 끝난 것입니다." + 5줄 시나리오. **재구매로 이어지는 문장**이므로 반드시 넣는다.

**그래서 무엇을 먼저 개선해야 할까?**
- 최종 결론 2문단. 두 번째 문단 끝에 "고칠 순서는 분명합니다. 먼저 ~, 다음으로 ~, 마지막으로 ~"
- 단기/중기/장기 각 5~6개, 앞 페이지 항목과 일관되게.
- 이 리포트의 한계: 긍정형. "N명이 처음 사용한 순간의 기록입니다. 시장 전체의 비율이 아니라 처음 만난 사용자가 어디서 막히고 어디서 좋아하는지를 보여주는 자료로 읽어 주세요. 오래 사용했을 때의 경험은 이번 개선이 반영된 다음 테스트에서 확인하면 더 정확해집니다."
- 맺음 인용: 4~5문장, 평이하게. 짧은 경구 금지.

## 머리말·꼬리말

- 머리말: `앱이름 | 사용자 피드백 보고서` (표지 제외)
- 꼬리말: 왼쪽 "앱이름 사용자 피드백 보고서", 오른쪽 두 자리 페이지 번호 "02"
